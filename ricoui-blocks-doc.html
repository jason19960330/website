01

它到底是什么

一句话：不是 npm 依赖，是把源码交到你手里的强视觉组件集。

  • 定位：RicoUI Blocks V1.0，官网 blocks.ricoui.com，MIT 开源，作者 @ricouii。基于 React 19、Tailwind CSS 4、TypeScript，专注落地页、作品集、产品展示和 AI 产品界面里「有明显视觉记忆点」的组件、交互与背景效果。
  • 补的空位：shadcn/ui 这类基础库覆盖按钮、表单、弹层，但不管网点波普插画、光学放大镜、ASCII 流动背景、多层幕布 Preloader。项目明确写了「不试图替代基础 UI 库，而是补足它们不覆盖的强视觉组件」。
  • Copy Source：安装后源码归你所有，随意改；没有运行时包、没有版本锁定。分发走两条路 —— shadcn Registry URL，或直接在官网组件页复制源码。Registry 只是分发协议，不代表依赖 shadcn/ui、Radix 或 cn()。
  • 动效优先：实体交互、惯性拖拽、序列动画；motion / gsap / three 按组件需要引入，并在 Registry 里逐组件显式声明，绝不偷偷带进来。
  • 零运行时锁定：不依赖 shadcn/ui，不依赖 TanStack Start，任意 React + Tailwind 项目可用 —— Next.js、Vite、TanStack、Astro + React / React Router 都行。官网自己用什么框架，与你无关。
体量：仓库创建于 2026-10-15，最近提交 11-13，约 44 star / 2 fork / 0 open issue。语言构成 TypeScript 约 78%、CSS 约 18%、HTML 约 4%，仓库约 18 MB。文档相当齐：AGENTS.md 加 docs/ 下项目规格、架构、开发流程、组件规范、Registry 与 Dither Pop 全套规范。
02

15 个组件 / 5 类

少而偏门，每一类都不是基础控件。

  • Dither Pop（4 个）：File Organizer、Flip Switch、Dither Progress、GitHub Repo。独立视觉系列，三渲二 2.5D 矢量插画语言 —— 深藏蓝描边、饱和蓝橙黄、规则半调网点、统一左上光源、有支点的实体交互；单独维护一套设计规范与四个组件专项文档。
  • Display（5 个）：Magnifier（光学放大镜）、Contribution Graph（网点贡献日历）、Empty States、Kubai Empty States、Social Card。Buttons 有 Button 与 Bell Button；Backgrounds 只有 ASCII Background（WebGL + Canvas 兜底）；Preloader 有 Popin、Clip Image、Step Overlap 三个多层幕布效果。
  • 依赖很克制：flip-switch 与 file-organizer 用 motion，三个 Preloader 用 gsap，其余组件零第三方依赖。Registry 里实际是 16 个 item，多出的 github-contributions 是 registry:lib 类型的服务端数据辅助函数，不算官网展示组件。
  • 独立 HTML 版：ASCII Background 与 Social Card 各有一份 .html，可从详情页复制或下载，不依赖 React 工程、不加载远程图片字体脚本；Registry 仍只分发对应的 .tsx，两版效果要人工保持同步。
  • 详情页给什么：每个组件页有 Preview、Props、Interaction Type、Dependencies 和源码；Interaction Type 是一句人话，例如「悬停把卡片扇开，再点击打开文件夹」。

03

三层架构与硬约束

官网、可分发源码、消费者项目，三层互不越界。

  • 官网层：TanStack Start + React 19 + Vite + TypeScript + Tailwind 4，部署在 Cloudflare Workers，负责路由、文档、组件 Preview 与人工策展的首页。src/routes/ 是路由，src/components/site/ 是官网自身 UI，src/components/previews/ 是演示画布，src/data/ 是组件元数据。
  • Registry 源码层：顶层 registry/ 放真正分发给用户的 .tsx / .ts 源码，registry.json 是清单，public/r/ 是构建产物。组件只能是 React + Tailwind，需要动效时按组件声明第三方包。
  • 消费者层：任意 React + Tailwind 项目。最重要的一条约束原文是 ——「网站可以依赖 TanStack Start，但 Registry 组件不能依赖 TanStack Start」；组件也不得引用 @/lib/utils、@tanstack/*、@/components/site/* 这类只在官网存在的东西。
  • 显式优于魔法：src/data/components.ts 是官网目录的唯一显式数据源；Preview 用 lazy 显式映射、Source Code 用 Vite ?raw 读真实 registry 文件，都不做文件扫描或 AST 自动解析。当前规模不用 monorepo、不提前优化。
  • Preview 与源码严格分离：Preview 可以提供背景画布、variant 切换、模拟内容，但这些代码绝不进入 Registry 组件；需要 helper 就组件内部实现，或作为 item 文件一起安装。官网 Demo 好看，不代表组件真能独立跑。
性能上最在意的点：组件库网站的压力不在普通页面，而在一屏里同时跑很多 Preview。规则是 GSAP / Three / WebGL 这类重型演示 lazy 加载、接近视口才初始化，长时间运行的 Canvas / RAF 动画离开视口要暂停，首页不一次拉起所有重型动画。
04

安装：Registry 与复制源码

一条命令装一个组件，不用装 RicoUI 这个包。

把 URL 末尾的组件名换成任意 slug

{{ texts.install }}
  • shadcn CLI 路径：npx shadcn@latest add https://blocks.ricoui.com/r/flip-switch.json，把 flip-switch 换成任意 slug。用到的 motion / gsap 会在安装时自动声明，不用手动处理；Registry item 的 files[].target 决定源码落到你项目的哪个路径（如 @ui/flip-switch.tsx）。
  • Manual 路径：完全不用 shadcn CLI 也能用 —— 打开组件详情页看 Dependencies，手动装包，再 Copy Source 把 .tsx 复制进项目并 import。README 明确写了「用户如果完全不使用 shadcn CLI，也能使用 RicoUI」。
  • 装完做什么：源码已经属于你，改颜色、改尺寸、改动效参数都直接改文件；组件默认带 className 与少量视觉 Props，方便覆盖。没有升级命令，也没有上游包版本这个概念。
  • 两条补充通道：ASCII Background 与 Social Card 有独立 .html，详情页可直接复制或下载；shadcn 也支持从公开 GitHub 仓库根的 registry.json 安装，但官网主入口始终是 blocks.ricoui.com/r/*.json。
一个常见误解：看到 npx shadcn 就以为必须先把 shadcn/ui 装进项目。不是的 —— 这里只是借用它的 Registry 分发协议，组件本身不依赖 shadcn/ui、不依赖 Radix、也不假定你项目里有 cn()。
05

组件规范与可访问性

目标是「拿走即可成为项目的一部分」，不是只能在 Demo 里成立的视觉实验。

  • 默认视觉：RicoUI 不是 Headless UI，组件应该有完成度较高的默认视觉，不该要求用户传十几个 class 才能复现官网效果；同时接受 className 与必要的视觉 Props 以便覆盖。
  • Props 克制：只暴露真正有使用价值的参数（如 color、size、className），不为「可配置」把每个动画中间值都做成 Prop。组件可以有自己的视觉 variant，与网站全局浅/深色无关。
  • 可访问性：键盘可操作、正确的 aria 属性与焦点反馈；明显运动型组件要合理处理 prefers-reduced-motion —— 用 CSS、useReducedMotion，或直接关掉非必要动画、减少位移。不要求取消所有视觉。
  • use client 不滥用：只有真需要 state / effect、事件处理、动效 runtime、window / document、Pointer / Canvas / WebGL / ResizeObserver / IntersectionObserver 时才加；纯静态 React / CSS 组件不机械加。它存在的意义是兼容消费者项目，不代表依赖 Next.js。
  • 依赖透明：允许 motion、gsap、three、@react-three/fiber 等，但 Registry 必须准确声明；无依赖的组件在官网直接显示「Dependencies None」。禁止隐藏依赖前文已列明。
  • 署名规则：原创组件不需要 Credits；Inspired 要写 Inspired by / 作者 / 来源，Based on 要写原项目 / 许可 / 来源；上游许可不明确时，不复制原代码。
浅色 / 深色怎么要求：普通 UI 与交互组件尽量兼容两种主题，但不强制细节完全一致；Effects / Backgrounds 这类纯视觉效果不强制，保持设计表达优先。这是很务实的取舍。
06

本地跑官网

Node.js 22.12+ 与 pnpm，每个新终端先 nvm use。

克隆 → 起服务 → 构建 / 预览 / 部署

{{ texts.dev }}
  • 版本要求：Node.js 22.12 或更高（.nvmrc 固定 22.23.3，是 Vite、TanStack Start 与 Wrangler 的共同要求），Node 18 跑不动当前工具链；包管理器用 pnpm。没装对应版本先 nvm install。
  • 可用脚本：pnpm dev 起开发服务器，pnpm build 生产构建并执行类型检查，pnpm preview 预览产物，pnpm deploy 构建并部署到 Cloudflare Workers，另有 registry:validate 与 registry:build。
  • 可选 GA4：把 .env.example 复制成 .env 并填 VITE_GOOGLE_ANALYTICS_ID，仅生产构建加载，本地开发不受影响。
  • 先读文档：参与开发前先读 AGENTS.md，再按需查 docs/PROJECT-SPEC.md、ARCHITECTURE.md、DEVELOPMENT.md、COMPONENT-GUIDELINES.md 与 Dither Pop 系列规范。仓库刻意保持目录浅、直接、可搜索。
  • 验证范围：只跑与本次修改相关的检查，局部改动不做全量重型回归；涉及 Registry、构建配置、部署或跨模块修改时才跑完整 build。
不要提前优化：开发文档明确列出「metadata 太多、Registry JSON 太大、Preview map 太长、分类太多」等问题在真实出现之前一律不处理，当前组件规模下显式手工配置是允许且被推荐的。
07

分发细节与新增组件

一个组件一次走完整条链路，最后一步必须是安装验证。

Registry 校验 / 构建 / 新增组件的固定流程

{{ texts.registry }}
  • 源与产物：根目录 registry.json 声明 name、homepage 与 items；每个 item 写 type（registry:ui / registry:lib）、title、description、dependencies 与 files[].path / target。shadcn build 生成 public/r/*.json，那是产物、不要手改。
  • 两种依赖别混：npm 包写 dependencies，Registry item 之间的依赖写 registryDependencies。校验以官方 CLI 为准，不自己另写一套 validator。
  • 固定链路：component source → preview → metadata → registry item → docs → install verification → next component。一个组件一次做完，不先批量建空壳；首页 Latest 按首次发布日期 publishedAt 倒序，日常改组件不更新这个日期。
  • 安装验证七项：schema 正确、文件存在、dependencies 完整、build 成功、public/r/*.json 生成、JSON URL 可访问、临时 React + Tailwind 项目里装完能跑。原文强调「官网 Demo 正常不等于 Registry 一定可安装」。
  • 分类与路由：五个分类通过 /components 的 filter / search params 实现，不为分类建独立路由，这样以后换分类不会改变详情页 URL；首页是人工策展，不是 Registry 自动生成的页面。
GitHub Registry：shadcn 也支持直接从公开仓库根的 registry.json 安装，但 RicoUI 把官网 blocks.ricoui.com/r/*.json 作为主入口，GitHub 只是补充，不需要同时设计两套用户界面。
08

适用判断、授权与限制

什么时候值得用，以及几条必须先知道的边界。

  • 适合谁：做落地页、作品集、产品展示或 AI 产品界面，需要一两个「让人记住」的视觉组件；已经是 React + Tailwind 工程，愿意把源码拿进来自己维护；看重键盘操作与减少动态效果这类细节。
  • 不适合谁：纯静态 / 非 React 项目（只有两个组件有独立 HTML 版）、只需要按钮表单表格这类基础控件、需要一套中性可换肤的设计系统、或希望「装个包然后等上游发版」。它的视觉主张很强，与既有设计系统混用通常要调色改源码。
  • 没有升级通道：源码一旦装进项目就与上游脱钩，上游修了问题要自己比对合并 —— 这既是「代码归你」的代价，也是它和 npm 组件库最本质的区别。
  • 授权要分开看：项目自有代码是 MIT（版权 2026 RICOUI，使用或分发要保留版权与许可声明）；但官网 TechText / PixelReveal 是 MIT + Commons Clause，本地字体遵循 OFL，Kubai Empty States 等基于他人作品重写的组件要在详情页保留 Credits 并遵循原始授权。别把「仓库 MIT」理解成「所有素材都能随便商用」。
  • 还很新：仓库 2026-10-15 创建、V1.0 只有 15 个组件、44 star，长期维护节奏与生态仍需观察。反馈与新组件方向走 GitHub Issues。
建议姿势：先去官网组件页挑一个真正用得上的（比如 Flip Switch 或 ASCII Background），用 npx shadcn add 装进一个临时项目跑一遍，看默认视觉与依赖是否合口味；确认顺手，再考虑把它放进正式页面并按需改源码。别一上来整套搬。
