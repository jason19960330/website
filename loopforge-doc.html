交付工作台 · 使用指南

LoopForge 完整指南

腾讯开源、可自主部署的团队工作台：在对话里把需求交给 Main Bot， 它按需打开 Docker 沙箱、检出仓库、把任务分派给项目角色，最后提交 PR。 某种做法被验证有效后存成 SOP，下一个需求按同样方式交付，关键节点由人把关。指南整理自其公开仓库。

01

它到底是什么

一句话：它不写代码，它编排写代码的 Agent。

  • 定位：自托管的「团队 × 编程 Agent」交付工作台，MIT 开源，官网 loopforge.cn。干活的是 CodeBuddy、Codex、Claude Code、OpenCode、Cursor CLI、Antigravity、Kimi Code、Pi、DeepSeek Harness、ZCode 这 10 种 CLI；LoopForge 负责它们外面的角色、沙箱、检查点和留痕，全部跑在你自己的环境里。
  • 要治的病：直接让 Agent「修一下这个 Bug」，结果取决于这一次运行 —— 可能跳过方案、忘了跑测试、自己评审自己的代码、做到一半停下没人发现。做演示没问题，团队交付不能这样。
  • 五条设计原则：可重复（同一条 SOP、同样阶段与检查）、角色分离（方案 / 实现 / 评审 / 测试各有独立提示词、执行器、模型、Skills 和 MCP）、人在回路（关键节点审批或打回）、可观测可续跑（节点状态、工具轨迹、日志、产物集中呈现）、技术栈和服务器都是你的。
  • 两种形态：平台版是 Docker Compose 起的一套 Web 服务（含 MySQL，默认 0.0.0.0:8090），给团队共享工作区与审批记录；Local 版是一个 npm CLI，把内置交付工作流直接装进你正在用的编程助手，不需要服务端。
  • 不是什么：不是通用自动化搭建平台，也不替代任何编程 CLI。它更像给这些 CLI 套上一层「谁来做、在哪个沙箱、按什么顺序、经过哪些检查、由谁签字」的工程外壳。
体量：约 867 star / 211 fork / 324 commits / 15 tags，最新提交 2026-11-14，MIT。语言构成以 Go 为主（约 59%），其次 JavaScript 约 23%、Python 约 9%、CSS 约 8%。仓库保留上游模块名 agentflow 与 AGENTFLOW_ 环境变量以减少合并冲突。
02

两种工作方式

探索和迭代用对话，固定阶段和签字用 SOP，两者挂在同一套需求上。

  • 与 Main Bot 对话：适合探索、快速修复、和 Agent 反复迭代。它按需打开「对话工作区」—— 一个带项目仓库的 Docker 沙箱，把项目角色作为原生子 Agent 调用；每个会话可单独选执行器、模型和确认模式。回复进行中发出的消息进排队托盘，「引导」可打断当前回复立即发送，生成的文件在侧边产物抽屉里预览、看源码、下载。
  • 运行 SOP：适合阶段固定、需要签字确认的可重复交付。引擎按顺序执行 Agent、脚本、人工关口和子 SOP，每次运行有独立沙箱；你在关口审批、打回到指定环节返工、从任意节点重试或重跑，交付物是文档、代码或 PR 加上每个节点的产物和日志。
  • 互操作：Main Bot 可以启动、暂停、恢复甚至接管正在运行的 SOP 工作区；对话里也能直接交付 PR 或直推共享分支（mode=direct）。所以不是二选一，而是按任务性质混着用。
  • 统一台账：无论改动来自对话还是 SOP，都能追溯到原始需求，并计入交付与成本统计；还支持 PR / MR 状态跟踪、合入检测。这点是「工作台」和「一堆散装 Agent 会话」的分界线。
  • 怎么选：需求还模糊、要来回试 → 对话；希望每个需求都按同一套做法交付，有固定的评审、测试和签字环节 → 沉淀成 SOP。项目里还内置了 AI 定时任务，可周期性派发 SOP。
功能面：除上述两者，还有流程设计器画布、可复用角色定义、集中处理的「待我确认」、研发效能与业务领域报表（可导出静态 HTML / SVG）、按公开标准价核算的 SOP 与对话 Token 成本，以及带 OpenAPI 描述的 HTTP 与 MCP API。管理页中英双语，对话工作台目前只有中文界面。
03

SOP 怎么跑

Agent、脚本和人在同一次运行里衔接，验收不通过可以打回上游重做。

  • 五类节点：Agent（一个角色负责设计 / 实现 / 评审 / 测试）、脚本（构建、测试、Lint、生成报告，不需要 AI 的地方就不用 AI）、人工关口（暂停等人检查，放行或打回）、子 SOP（复用另一条流程）、预览构建（构建静态站点并归档供评审）。每个节点声明自己的产物与依赖，依赖完成引擎自动推进。
  • 角色是复用的：提示词、执行器、模型、规则、Skills、MCP 工具、产物与门禁打包成一个角色定义，SOP 节点和对话里的子 Agent 共用同一份；同一角色还能在画布上单独换执行器和失败策略。
  • 关口有三种动作：确认通过继续下游、补充信息重跑当前节点、退回上游重做。运行详情里实时显示节点状态、工具轨迹、Worker 日志、节点产物快照和工作区预览。
  • 内置四条只读蓝图：通用后端交付、通用前端交付、通用缺陷修复、通用产品方案。复制到本项目后才能运行和修改，随流程演进可发布新版本。流程设计器支持失败打回、配置检查与版本历史。
  • 一次真实交付：四个 CodeBuddy 角色依次完成一个 Python 修复的规划、实现、独立评审和交付汇总，三个真实测试通过，运行停在人工关口等批准，批准后再验证代码与验收时一致。这条链路已沉淀成可复用验收用例，覆盖范围和未联调项写在实测记录里。
为什么要「独立评审」：同一个上下文里让 Agent 自己评自己的代码，很容易一路放行。把评审拆成独立角色、再接一段确定性脚本测试、最后才交给人签字，是这个项目最核心的一条工程约束 —— 也是它和「给 Agent 套个漂亮提示词」的区别。
04

自主部署与免 Key 体验

三条命令起服务，不在本地构建镜像，也不需要宿主机装 Go 或 Node.js。

克隆 → 启动 → 服务管理 → 核对镜像摘要

{{ texts.deploy }}
  • 前置与安装：安装脚本检查 Docker、Compose、Python 3 和 curl，确认后可补装缺少的组件（Linux 支持 apt / dnf / yum，macOS 走 Homebrew）；直接拉 compose.yaml 里 pin 的 GHCR 发布镜像，顺手创建 MySQL 与平台服务、生成配置和会话密钥、导入内置沙箱、通用 SOP 和体验项目。LOOPFORGE_YES=1 可接受安装提示。
  • 首个账号：打开脚本输出的地址创建账号，第一个自动成为管理员；云主机上脚本会从元数据服务读公网 IP 直接打印，放通安全组端口或配 HTTPS 反向代理即可访问。管理员账号创建前建议只允许自己的 IP 访问。首页「快速接入」带你配模型凭据、绑定仓库、选默认 SOP。
  • 国内镜像：把 MIRROR 设成可替换 ghcr.io 的镜像站主机名，脚本用它拉取后再把镜像标回 compose.yaml 里的官方名 —— 设置它等于信任该主机。发布说明里有 digest，用 docker image inspect 核对。Docker 引擎的 registry-mirrors 只加速 Docker Hub，不能填在这里；升级时带同一个变量执行 pull。
  • 零成本先跑通：新账号自动加入「LoopForge 体验项目」，其中有一条只含脚本和人工审批的 SOP。切到体验项目 → 流程模板 → 平台验收·脚本与审批 → 运行流程；真实脚本生成报告后停在关口，在「待我确认」或运行详情页批准，就能看到流程继续并产出最终产物。这一步不需要任何 API Key。
  • 真实任务要什么：与 Main Bot 对话、生成文档或新项目需要所选执行器的 API Key；要修改已有仓库并提交 PR，还需要模型凭据加上在个人设置里连接 GitHub（内置授权应用走设备码，也可手填 PAT）。GitLab、Gitea、Gogs 可配 Git SSH；CNB 官方仅支持 HTTPS 加访问令牌。Issue 与 PR / MR 自动化另需托管平台 API Token 或配置 MCP。
GitHub 不是必需的：所有内置通用 SOP 都能不绑仓库运行 —— 产品方案交付文档，前后端新项目在任务工作区交付源码；只有缺陷修复仍需提供待修代码和复现材料。先跑通免 Key 体验，再决定要不要接凭据，是最省事的试法。
05

Local 版：装进编程助手

不想部署服务端？一条 npx 把交付工作流带进你正在用的 IDE / CLI。

Classic Edition（默认）：Node.js 20+ 与 Python 3.8+

{{ texts.local }}
  • 工作流五步：先理解问题（调研现有项目、澄清目标与验收标准，而不是立刻写代码）→ 确认边界后再实施（中大型任务要你确认目标、范围、排除项、关键决策）→ 分工完成交付（设计、实现、审查、测试由独立角色分阶段做）→ 用证据说明结果 → 中断后继续执行（状态已保存，下次从没做完的阶段接着跑）。
  • 按复杂度分流：小改动走精简的单角色路径「理解 → 实现 → 自检 → 交付」；中大型任务才启用完整链路「澄清并确认 → 设计 → 实现 → 独立审查 → 测试 → 交付」。不会为简单任务硬套流程。
  • 产物留在本地：一次任务结束同时得到代码变更、已确认的需求、技术方案、独立审查意见、测试结果和交付总结，默认写在 artifacts/{task_slug}/，按 01-requirement 到 05-knowledge 分目录，另有 workflow-summary.md。Classic 中断后可用 /resume-devflow 恢复。
  • 宿主与版本：CodeBuddy、Codex、Cursor、Claude Code 四种支持 Classic（默认）与 Portable；Pi、DeepSeek Harness、Hermes Agent 只支持 Portable。同一项目里，每个编码 Agent 只能启用一种 Edition，切换要重新安装并加 --force，先跑 loopforge plan 看会写哪些文件。
  • 本地可观测看板：CodeBuddy 的 Classic 版内置一个纯本机看板，把落盘证据变成会话活动、Token 与成本趋势、Skill / Rule 使用、角色派发和阶段归因视图。数据聚合与页面服务都在本机，不依赖外部遥测；但运行日志可能含工具参数和输出片段，默认排除在 Git 之外，未经检查别外分享原始日志。

Portable Edition 与长期维护（安装状态写在 .devflow/install-state.json）

{{ texts.portable }}
平台版与 Local 版怎么选：平台版适合团队共享对话工作区、SOP、审批与运行记录，依赖 Docker 加 Python 3；Local 版适合个人开发者在 IDE / CLI 里用，依赖 Node.js 20+、Python 3.8+ 和一个编程助手。证据留存上，前者是 Web 工作台里共享的运行详情、审批与指标，后者是本地产物目录加可选看板。
06

架构与执行器

Go 单体 + MySQL，internal/engine 管调度，执行器协议与沙箱生命周期分开。

  • 目录分工：cmd/agentflow 是 API、Worker 或合并进程；cmd/agentflow-runner 是个人与池化执行机器；cmd/agentflow-mcp 与 cmd/agentflow-gate-mcp 提供公共 MCP 和结构化关口结果；internal/engine 管 SOP 图、租约、调度、沙箱生命周期与交付（就绪分支在同一运行工作区一起执行，取消后重跑一条分支会恢复被取消的兄弟节点）。
  • 其余层次：internal/repo 是 MySQL 持久化，按业务域一个 repository；internal/httpapi 按业务域一个 handler；internal/runtime 与 internal/runner 管执行器协议、凭据、隔离与产物；internal/tracker 适配远端 Issue / PR；web 内嵌上游界面与登录；migrations 是显式数据迁移；local 放本地工作流与宿主集成。
  • 公开版增量：账号密码登录和 GitHub 适配器接入现有的 user / token / repository / delivery 契约，没有另起一套引擎或内存生产存储。以 github: 开头的远端仓库标识用来区分 GitHub 的 owner / repository 与旧 tracker 标识，兼容字段仍叫 gongfengProjectId。
  • 10 种执行器凭据不同：CodeBuddy 可用个人 Key 或管理员配的平台共享 Key（镜像内置）；Codex、Claude Code 可用个人 Key 或已连接执行机器上的本机登录；OpenCode、Kimi Code、Pi 仅个人 Key；DeepSeek Harness 镜像内置；Cursor CLI、Antigravity 首次在对话里用厂商脚本安装、不进 SOP 沙箱；ZCode 需自己装进 PATH。Claude Code 之后的 7 种 CLI 每次运行都在私有 HOME 生成模型与 MCP 配置，因此团队里每人都要各配自己的 Key 和 Base URL。
  • 几处刻意的边界：需求澄清、通知 AI 汇总、Bot 回复和运行评测目前固定用 CodeBuddy，服务端收到其他 CLI 的模型会直接拒绝并说明原因，不会悄悄替换；定时助手任务用任务所选的执行器。CLI 的 Classic / Portable 工作流资产彼此分离，也不与平台角色定义共用运行时资产。

07

安全边界与部署红线

面向可信团队设计，不是不可信多租户的隔离边界。

  • Docker socket 是最大权限点：默认 Compose 安装里，SOP 运行和对话工作区都由平台通过宿主机 Docker socket 启动容器，等于给了平台控制宿主机 Docker 的能力。README 明确写了这只适用于可信团队，不构成不可信多租户隔离边界；重复执行安装脚本会保留已有数据。
  • 默认监听与注册：新安装默认监听所有网卡（已有安装保留原配置），已登录用户能读实例内各项目数据，团队成员可在登录页自助注册。在 .env 里设 AGENTFLOW_ALLOW_SIGNUP=false 可关掉注册；对团队以外开放前必须阅读账号与访问边界并配好 HTTPS 反向代理，管理员账号创建前只放自己的 IP。
  • 凭据由你自己管：平台不附带模型额度，Key 和 Base URL 由每位成员在个人设置里填；部分执行器首次安装需能访问 npm 或厂商站点。GitHub 走内置授权应用的设备码，也可手动填 PAT；不要把凭据、私有地址或生产运维配置写进工作流模板。
  • 本地侧也要看一眼：部分宿主的 Classic 配置会启用自动执行或高权限 Agent 模式，只在可信项目里用；安装前用 loopforge plan codebuddy（或对应宿主名）检查将写入哪些文件。检测到你改过文件或有冲突时更新会停下，只有确认替换或切换 Edition 才加 --force。
  • 报告漏洞的方式：按仓库安全政策走 GitHub Security Advisory 私密报告，不要开公开 issue。远程访问、HTTPS、独立 Worker、原生部署需装哪些 CLI，都在部署指南里。
一个容易忽略的细节：设置 MIRROR 意味着信任那台镜像主机，因为下载结果会被标成官方镜像名。所以升级时务必带同一个变量，并用发布说明里的 digest 核对镜像摘要，别只看 tag。
08

适用判断与限制

什么时候值得上，以及几条必须先知道的边界。

  • 和 Dify / n8n / Flowise 的区别：那些是通用的 AI 或自动化工作流搭建平台；LoopForge 只专注「用编程 Agent 做软件交付」—— 实现者与评审者的角色分工、带真实仓库的 Docker 沙箱、GitHub 交付、人工验收关口和运行证据。
  • 和直接用 CLI 的区别：它不替代 CodeBuddy / Codex / Claude Code，每个 Agent 步骤和每轮对话仍跑这些 CLI 之一；它补的是外面的部分。如果你只是一个人改一个小函数，直接开 CLI 更轻。
  • 适合谁：需要把「方案 → 实现 → 独立评审 → 测试 → 签字」固定下来的团队；已经有多套 Agent CLI、想统一角色、沙箱、凭据与成本口径的场景；需要交付记录可检查、可复盘、可续跑，或者要用定时任务周期性派发交付的人。
  • 明确未实现：平台 SOP 导出后在本地独立执行还没做，Local 目前只跑内置 Classic / Portable 工作流；内置 SOP 是平台维护的只读蓝图，要改得先复制到本项目；对话工作台目前只有中文界面。内置通用 SOP 不绑仓库时，缺陷修复仍需你提供待修代码与复现材料。
  • 不适合谁：没有 Docker 环境、只想做一次性代码补全、需要面向不可信用户做多租户隔离、或期待「一句话自动出成品、完全不用人把关」的场景。它把人放在关口上，这是特性不是缺陷。
建议姿势：先用体验项目那条纯脚本加审批的 SOP 走一遍「运行 → 报告 → 人工批准 → 继续」，完全不用 API Key；顺手在目标项目里装一次 Local 版，感受内置交付工作流；确认这两步顺手，再考虑部署平台版、接模型凭据与 GitHub。别一上来就把整套团队流程搬进去。
