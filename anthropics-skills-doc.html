01

它到底是什么

一句话：不是工具集，是「Skill 该怎么写」的标准库。

  • 定位：Anthropic 官方维护，仓库 anthropics/skills，描述只有一句「Public repository for Agent Skills」。Skill 是「装着指令、脚本与资源的文件夹」，Claude 动态加载它，把某类任务做得更稳定、可复现。
  • 四个部分：spec/ 只有一句指路（规范正文已独立到 agentskills.io）；template/ 是 3 行 frontmatter 的最小模板；skills/ 放 19 个范例；.claude-plugin/marketplace.json 把它们编成 5 个插件包。另有 THIRD_PARTY_NOTICES.md 记第三方素材。
  • 文档处理那 4 个是特例：docx / pdf / pptx / xlsx 正是 Claude 文件能力的底层实现，是「复杂技能在真实产品里怎么落地」的参考，比纯示例更值得读。
  • 官方自己划的边界：README 用粗体写明——这些技能仅供演示与教育，你从 Claude 实际拿到的行为可能与这里不同；关键任务前务必在自己的环境里充分测试。
体量：仓库 2025-09-22 创建、最近推送 2026-11-14，约 195k star / 23k fork / 1.5k open issue，主体语言 Python（文档技能带大量脚本），约 5.4 MB / 544 个路径。根目录没有统一 LICENSE 文件。
02

19 个 Skill / 5 个插件包

先按分组找最接近的范例，别 19 个全读一遍。

  • 按插件包：document-skills 4 个（xlsx / docx / pptx / pdf）、example-skills 12 个、claude-api / academy-guide / discernment-nudge 各 1 个，合计 19。
  • 按用途：文档处理 4 个、创意与设计 6 个（生成艺术、品牌规范、海报、前端视觉、Slack GIF、10 套主题）、开发与技术 4 个（MCP Server、HTML artifact、Playwright 测试、Claude API 参考）、写作与引导 5 个（skill-creator、文档共创、内部沟通、课程推荐、事实核查追问）。
  • 复杂程度差很多：claude-api 单份 SKILL.md 617 行、约 10 万字符，带 csharp / go / java / php / python / curl 多语言示例；pptx 272 行、28170 字符；canvas-design 一个技能带 84 个文件（含字体）；brand-guidelines 只有 74 行正文加一个许可证。
  • 多数带附属资源：文档四件套与 webapp-testing 有 scripts/，pdf 拆出 REFERENCE.md / FORMS.md，mcp-builder 拆出 reference/，skill-creator 带 agents/、eval-viewer/、scripts/。这些正是第 04 节要讲的分层。

03

SKILL.md 格式规范

必填字段只有两个，难点全在 description。

最小可用 SKILL.md + 全部字段约束

{{ texts.frontmatter }}
  • 结构：一个目录一份 SKILL.md，YAML frontmatter 后接 Markdown 正文，正文没有格式限制，建议写步骤、输入输出示例与常见边界。目录里可再放任意文件。
  • name：1–64 字符，只用小写字母、数字与连字符，不以连字符开头或结尾、不含连续连字符，且必须与所在文件夹同名。
  • description：1–1024 字符，同时写清「做什么」与「什么时候用」，并带上能帮模型对上任务的关键词。规范给的反例是「Helps with PDFs.」，正例会写明提取文本表格、填表单、合并 PDF，以及「用户提到 PDF、表单、文档提取时」。
  • 可选字段：license（简短协议名或随包文件）、compatibility（≤500 字符，说明环境要求，多数技能不需要）、metadata（string → string 映射）、allowed-tools（空格分隔的预授权工具，实验性，各实现支持不一）。
  • 校验：官方参考实现 skills-ref validate ./my-skill 会检查 frontmatter 与命名约定；本仓库 template/SKILL.md 就是 3 行 frontmatter 的起点。
描述要写得主动一点：本仓库多个技能的 description 直接列出触发词与「Do NOT use for…」排除项。模型往往在该用的时候反而不主动调用，把边界写清楚比写得漂亮更重要。
04

三层渐进式披露

这是 Skill 与普通提示词模板最本质的区别。

  • 第一层 · 元数据（约 100 tokens）：所有技能的 name + description 在启动时就进上下文，供模型判断这一轮该不该用。所以描述写得含糊，技能等于不存在。
  • 第二层 · 指令（建议 < 5000 tokens）：技能被触发后才把整份 SKILL.md 正文读进来。规范建议正文控制在 500 行以内，超了就加一层目录并写清「接下来该去读哪份」。
  • 第三层 · 资源（按需）：scripts/ 放可执行代码（脚本可以直接跑，不必读进上下文）、references/ 放按需查的文档、assets/ 放模板 / 图片 / 字体等产出用素材。单份参考文件保持聚焦，超过 300 行配个目录。
  • 引用规则：从技能根目录写相对路径，尽量只引一层，避免 A 引 B、B 再引 C 的深层链；pdf 把表单细节放 FORMS.md 就是典型做法。
  • 多领域怎么拆：一个技能要覆盖多个框架时，按变体分文件（references/aws.md、gcp.md、azure.md），正文只写工作流与选型，模型只读相关的那一份。
为什么值得这么拆：加载进来的东西越少，留给任务本身的上下文越多；而脚本可以「不读也能跑」，等于把确定性工作外包给代码，模型只负责判断与编排。
05

在 Claude Code / Claude.ai / API 里用

三条入口，都不需要 clone 下来自己装。

插件市场命令 / 网页端 / API 入口

{{ texts.install }}
  • Claude Code：先用 /plugin marketplace add anthropics/skills 把这个仓库注册成插件市场，再 /plugin install document-skills@anthropic-agent-skills 之类按包安装；也可以在「Browse and install plugins」里选 anthropic-agent-skills 勾选安装。装完直接提需求即可。
  • Claude.ai：付费计划里这些示例技能已经内置；自定义技能可从设置里上传，用法见官方「Using skills in Claude」。
  • Claude API：Skills API 支持 Anthropic 预置技能与上传自定义技能，入口在 docs.claude.com 的 skills-guide；服务端用法与本地文件夹是两套装载方式。
  • 只是想学写法：直接看 spec/、template/ 与 19 个 SKILL.md 就够了，规范全文在 agentskills.io/specification。
触发不是关键词硬匹配：技能以 name + description 出现在可用列表里，模型自行判断是否查阅；简单一步就能完成的任务，即使描述完全对上也可能不触发。
06

skill-creator 的评测循环

19 个范例里最值得学的那个，把「造技能」做成可迭代的工程流程。

  • 从意图到草稿：捕获用户想解决什么 → 访谈与调研补齐边界 → 写 SKILL.md 与附属资源 → 造一批贴近真实口吻的测试用例。
  • 同轮对照实验：每条用例在同一轮同时启动「带技能」和「不带技能」两组运行，别先跑完一组再补对照组；跑的过程中边写量化断言、边记录耗时，结果落到 <skill-name>-workspace/iteration-N/eval-ID/。
  • 给人看，再迭代：评分聚合后启动 eval-viewer 让人对比产出，读反馈再改：从反馈里泛化而不是过拟合、删掉没在起作用的指令、尽量解释「为什么」、把多次重复写出的辅助脚本沉淀进 scripts/；然后重跑全部用例进下一轮，直到反馈为空或不再有明显提升。
  • description 单独优化：生成 20 条触发用例（8–10 条应触发、8–10 条「关键词相近但不该触发」的近似误触），交用户确认后跑优化循环，最后把 best_description 写回 frontmatter 并报告前后分数。
  • 沟通分对象：这份技能还专门提醒面向非技术用户时别直接甩 JSON、assertion 这类词；另有 Claude.ai 与 Cowork 环境下的专门分支说明。
目录本身就是教程：skill-creator/ 带 agents/、assets/、eval-viewer/、references/、scripts/，486 行正文；想给自己的团队定一套造技能流程，照它的骨架改最省事。
07

写一个自己的 Skill

最小版本只有 4 行，剩下的都是按需加。

目录结构 / 校验 / 评测 / 触发调优，一屏复制

{{ texts.create }}
  • 先只写 SKILL.md：用 template/SKILL.md 起手，name 与目录同名，description 把「做什么 + 何时用 + 触发词」写全，正文用祈使句列步骤与示例。
  • 再按需加资源：重复且要求确定性的动作写成脚本放 scripts/；长文档拆进 references/ 并在正文指路；模板、字体、图片放 assets/。别一上来就堆目录。
  • 校验与实测：先跑 skills-ref validate 查格式与命名，再拿几条真实提问试触发；重点看「本该用却没用」和「不该用却用了」两类偏差，回头改 description。
  • 别把示例当生产实现：文档四件套依赖不少 Python 库与二进制工具，直接搬进自己的环境前先看清它们的 requirements 与平台假设。
建议顺序：照着最接近的一个范例复制目录 → 只改 frontmatter 与正文跑通一条用例 → 加一组对照评测 → 再决定要不要拆 references、写脚本。一次写满所有分层，通常只是把提示词变长。
08

适用判断、授权与免责

什么时候值得读，以及几条必须先知道的边界。

  • 适合谁：要给 Claude / Claude Code / 兼容 Agent Skills 的助手写自定义能力；想搞明白「为什么技能比一段长提示词好用」；需要一个带对照评测的造技能流程；或者要参考生产级文档处理技能怎么组织脚本与参考资料。
  • 不适合谁：只想在 Claude.ai 里用现成功能（付费计划已内置，不必读源码）；要的是一个开箱即用的独立软件；或者期待把这里的技能搬过去就等于线上 Claude 的行为 —— README 明确说可能不一样。
  • 授权要分开看（* 号说明）：GitHub 仓库根没有统一 LICENSE 文件（API 返回 license: null）；19 个技能里 18 个在各自目录带 LICENSE.txt，README 说明多数为 Apache 2.0，doc-coauthoring 没有随附；第三方素材另见 THIRD_PARTY_NOTICES.md。别把「多数 Apache-2.0」理解成「整个仓库都是」。
  • 规范与实现分离：格式标准以 agentskills.io/specification 为准，本仓库是 Anthropic 的实现加示例；spec/agent-skills-spec.md 只剩一句指路，别拿它当规范全文。
  • 免责声明：这些技能仅供演示与教育用途，关键任务前务必在自己的环境里充分测试；allowed-tools 等实验字段各实现支持不一。
建议姿势：先读 template/SKILL.md（4 行）与 brand-guidelines（74 行）建立手感，再看 pdf 怎么拆参考文档，最后通读 skill-creator 的迭代循环。规范页留作字段速查即可。
